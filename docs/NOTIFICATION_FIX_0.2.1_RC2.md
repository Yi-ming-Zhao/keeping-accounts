# 0.2.1-rc2：未打开订单页时的通知采集

> 历史候选包记录。2026-10-21 使用者明确要求发布正式版并自行使用反馈；下文的候选状态和发布门槛只描述当时决策。正式版状态以 [0.2.1 发布记录](RELEASE_0.2.1.md) 为准，真机验证缺口仍保留。

2026-10-21。候选验证包，未发布正式版；用户真机问题尚未关闭。

## 用户提供的实际场景

- vivo X100 Pro，当前安装 0.2.0。
- 京东通过微信付款，付款后没有打开订单详情。
- 微信、京东、拼多多均已授权；系统通知读取、页面读取开关均开启。
- 用户不确定付款时是否出现通知，暂无可连接的真机。

因此，上一轮订单页面修复不能作为这次故障已解决的证据。此次修复针对系统通知，不要求打开订单详情；没有改动页面读取频率，也没有自动授权新的应用。

## 修复范围

- 支持严格匹配的支付来源标题带消息数量，例如 `[1条]微信支付`、`微信支付（2条新消息）`；不会用“包含微信支付”这样的宽泛条件匹配普通联系人。
- 读取 Android 的逐条消息字段，按消息发送者筛选微信支付，保留每条消息自己的时间，避免只处理最后一条或拼成一笔。
- 对通用“微信”标题，只提取明确以支付来源开头、字段独立完整的一行；不附带相邻聊天内容。
- 折叠通知的各行分别解析，不把两笔同额付款拼接成一笔。含多笔交易标识的平面正文拒绝按单笔处理。
- 支持“支付成功，实付款：6.38元，商户：京东”这类同行字段；仍按实付优先，不把商品原价 10.00 元当作实付。
- 逐条消息重新推送时使用消息时间识别重复事件。字段不足或金额冲突保持未知，普通聊天不交给模型。
- 结构化汇总通知只有具备交易或订单标识时才处理，避免汇总与子通知重复入账；不能隔离支付消息的汇总仍跳过。

Android 提供的消息、发送者和时间字段依据 [MessagingStyle.Message](https://developer.android.com/reference/android/app/Notification.MessagingStyle.Message) 与 [Notification extras](https://developer.android.com/reference/android/app/Notification)。这些是系统接口说明，不是微信当前版本通知格式的证明。

## 验证证据

测试通知由独立样本应用发布，Android 通知监听服务接收，最终检查加密账本；样本应用始终显示“首页”，没有打开任何订单页面，也没有发起付款。

- 修复前：`.local/notification-red.log`，同行金额通知、两条付款消息通知均未生成预期账目，2 项失败。
- 修复后调试包：`.local/notification-green.log`，相同 2 项通过。
- 单元检查：`PaymentNoticeContentTest` 6 项，覆盖来源筛选、聊天隔离、摘要边界、折叠行、金额冲突、币种和千位分隔符；`ReceiptParserTest` 13 项，保护原有金额及退款规则。
- 签名包：`.local/notification-rc2-validation.log`，检查 0.2.0 覆盖升级；同行通知；多消息通知及重复推送；无订单号的两笔同额消息及重复推送；监听器重连与新增授权后的补读；Android 原生消息和折叠格式的读取。

测试构造的消息标题和正文只证明代码对这些输入的行为，不能宣称已使用真实微信应用、真实微信支付通知或 vivo 后台环境验收。

## 未解决的证据缺口

仍不知道那次付款通知的实际标题、正文和通知结构，也没有服务连接状态的真机证据。权限开关开启不等于服务当时已连接。仅凭目前信息，不能认定唯一漏记原因。

如果微信没有提供可读的支付通知，付款结果页也没有被采集到，应用不能凭空得知支付事实。仅有付款金额时先记金额、保留商品未知，不生成虚构商品或分类。

包版本 `0.2.1-rc2`，versionCode 4，使用原签名；保持为本机验证包。正式发布仍需来自真实使用的触发证据，不要求用户专门为测试付款。
