# 青账 0.3.0：让 agent 识别尚未入账的交易

2026-10-22，versionCode 6。沿用原签名、包名和数据库结构，可从 0.2.1 覆盖升级。

## 问题与变更

此前固定解析器是入账前唯一入口：无法识别的通知直接丢弃，agent 只能给已有账目补分类。通知出现了、订单打开了，也可能始终没有账目。0.3.0 增加持久化候选证据与 agent 入账工具。

- 固定解析器只承担明确格式的快速入账。授权来源里的其他疑似交易文字先在本地过滤隐私字段、保存证据和任务，再交给官方 Pi agent 判断。
- agent 使用完整语义区分已付款、先用后付待扣款、退款、还款、转账、未支付、广告和无法确定的内容。原生工具验证金额和状态引用确实来自证据；缺少金额不补造，普通对话不能调用自动识别工具。
- 待识别证据会出现在待核对中；未配置模型、任务失败或不确定都有可见状态。任务和证据落在本机加密数据库，重启可恢复待执行任务，重复工具提交不会再次入账。
- 补充微信支付分、银行公众号和招行 95555 短信来源隔离；招行应用未授权时，首页和采集设置显示授权入口，不擅自扩大授权。
- 修复银行卡“消费人民币……”描述、先用后付使用通知、没有成功横幅但有实付的订单页，以及金额整数和小数分成节点的情况。
- 修复隐私过滤误删“确认收货后扣款”的语义。收货人、地址、联系方式和银行卡号码继续过滤。
- 页面不再只依赖固定标题，包含金额的可见页面可进入候选识别；微信普通聊天、输入区域和密码页仍隔离。已开启本机图片识别时，可对文字节点为空的非微信页面在本机识别截图；不绕过系统截图限制。

## 验证证据

构造样本不是来自用户手机的真实通知；没有登录支付应用，也没有发起付款。

- 原有逻辑在新增 7 项支付格式检查中失败 6 项。修复后同一组检查和原有金额规则通过。
- 真实模型测试经独立样本应用发布通知，Android 监听器保存候选证据，WorkManager 唤起官方 Pi，通过用户配置的 DeepSeek 接口调用原生识别工具。测试始终停留在样本首页，未打开订单详情。
- 两段固定解析器返回空结果的新措辞，分别生成 6.38 元支出与 28.80 元待扣款；一段商品广告被标为非交易，无支出。支出完成分类，Pi 对话持久化中包含实际识别工具调用。另一个纯图片订单经过真实系统截图、本机文字识别和 Pi，成功生成 6.38 元账目；即使金额标签被识别错，仍依据保留的上下文与数值入账。
- 原生检查覆盖金额和状态引用校验、拒绝编造金额、重复提交、不确定状态与隐私过滤。
- 签名包通过 15 项采集服务、6 项原生工具和通知格式、2 项界面检查。最后收紧不可见节点处理后，补验密码页、输入框订单页和图片页 3 项。0.2.1 覆盖升级保留账目、证据、用户修正锁定和设置。签名、体积和凭据检查见发布附件 `verification-0.3.0.json`；对应检查源码一并提供。

本次排查还发现，测试中用来定位订单的长数字会被通用脱敏删去，以及“收货”过滤范围过大、截图冷却时间跨窗口共用。修复后重新验证相关路径，没有把先前失败的检查写成通过。测试工具自身的 Kotlin 返回类型和弹窗清理问题也已修正；相关检查重新通过。

## 使用与边界

升级直接覆盖安装，不要卸载。agent 识别需要在设置中保存支持工具调用的模型接口；模型未配置或网络不可用时，候选会保留在待核对中。银行通知来自招商银行、掌上生活或短信应用中的哪一个，就需要授权对应来源；京东授权不等于招商银行授权。

这里只在用户已授权范围内读取系统提供的信息，不自动打开、点击或翻页。系统没有给出可读通知、可见文字或允许读取的图片时，仍无法获取交易。只有金额证据时不编造商品。缺乏共同编号的跨来源记录不按金额、时间强行合并，可能需要核对。

没有 vivo 真机和当前微信、京东、拼多多版本的实测证据，因此不能把构造样本与真实模型验证写成“任何支付均已覆盖”。当前采用人民币自动入账，外币进入人工核对。
